## 升级前必须知道

1. **数据库与会话兼容性**：本次 2.19.0 更新不包含数据库 Schema 变更（维持 SQLite schema 21 / Redis schema 13），无需执行停机迁移脚本，已有用户会话与分享数据均保持兼容。
2. **API 自动化客户端**：合法 API Key 调用的速率限制已解除无差别 1 QPS 反压限制，自动化集成与高频上传脚本将获得原生性能；若客户端曾依赖旧限流行为，无需任何适配。
3. **SSE 客户端并发连接**：上传状态监听连接现在强制执行单用户最多 10 个并发连接约束。若前端或第三方客户端在单会话内打开超过 10 个未关闭的 EventSource 连接，多余连接将收到 `429 Too Many Requests`，请确保客户端及时调用 `eventSource.close()`。
4. **反向代理配置**：若部署在反向代理（如 Nginx、Traefik、Caddy）后，请确保正确传递 `X-Forwarded-For`、`X-Forwarded-Proto` 或 `Forwarded` 标头，以便 SSE 配额与未认证防暴破限流准确按来源客户端生效。

## Upgrade notes (English)

1. **Database schema and compatibility.** SupaShare 2.19.0 introduces no database schema changes (retaining SQLite schema 21 and Redis schema 13). Existing sessions, shares, and configurations remain fully compatible.
2. **API automation.** Legitimate API calls are no longer throttled by the 1 QPS rate limiter intended for unauthenticated failed attempts. High-frequency automation pipelines will experience significantly reduced latency without client-side modifications.
3. **SSE connection limits.** The `/uploadStatus` SSE endpoint now enforces a quota of 10 concurrent connections per authenticated user (500 total). Ensure client applications properly close unneeded `EventSource` instances to avoid `429 Too Many Requests` responses.
4. **Proxy configuration.** When deploying behind reverse proxies, ensure proxy headers (`X-Forwarded-For`, `Forwarded`) are properly configured so that per-IP brute-force protections and per-user SSE connection quotas operate accurately.

本增量取代 ADR-017 中「所有公开预约固定 24 小时、没有续期」的选择，补充 ADR-015 的接收公平性和读截止。保留单进程、SQLite/Redis provider、既有 API 字段和账本 schema；不增加队列、后台线程或管理界面。

## 预约期限与清理

1. 公开 File Request 新预约只有 **5 分钟初始租约**。绑定总大小不算进展。已存在但仍未绑定的旧预约也按创建时间加 5 分钟判定有效期，不需一次性改写账本。
2. 持久化成功的新非空分片使租约延长到当前时间加 **15 分钟**，绝不超过创建后 **24 小时**。重复片、零字节、声明变更、失败写入不能续租。HTTP 层原有最小分片要求继续生效（1 或 5 MiB，最后剩余片例外），不允许反复用单字节新片续租。
3. 验证完整覆盖并 Claim 后，恢复创建后 24 小时的有限处理预算，容纳服务器加密和发布。空文件也必须走完整覆盖/Claim；它不能只靠空片延长预约。
4. 同一 File Request 最多 **1 个未取得进展的活动预约**，每 60 秒最多 **6 个新预约**。原有 owner/request/实例额度照常叠加。相同 ID 幂等重试不额外计数。请求能力是共享 bearer，不能将这些限制误称为对每个持有人独立公平。
5. 公开新预约前按 request 范围主动尝试清理到期会话，不再仅依赖每小时清理。使用原会话 gate；忙碌会话立即跳过，不等待、不误删。只有停止 I/O、关闭并删除自有 staging 确认后才释放额度；清理错误保留额度。
6. 从未绑定且已确认清理的终态回执保留 5 分钟，限制 reserve/cancel 对回执表的消耗。已绑定、完成及清理不确定的记录不缩短原有保留规则。公开预约 ID 仍由服务端随机生成，客户端不能指定复活旧预约。

旧的已绑定会话不被批量改成短租约，避免把升级中的活动上传直接判过期；新进展继续受到绝对上限。升级应先停写和排空旧进程。

## 接收正文的时间与公平预算

- 所有生产整文件/分片入口以服务端确认的 owner 和 File Request 作用域接入 receiver。
- 每个 owner、每个 File Request 各最多占 `max(1, 全局槽数/2)` 个槽。全局默认 4 槽时单主体最多 2；配置仅 1 槽时仍允许 1 个请求。
- 从开始接收到首个有效进展窗口最多 **60 秒**。每累计 **64 KiB wire 字节**才刷新 60 秒预算；一字节滴流不刷新。整个接收最多 2 小时，同时遵守更早的请求 context deadline。
- 在原始正文读取器上实施 HTTP `ResponseController.SetReadDeadline`，覆盖 multipart 首边界、header、普通字段、payload、尾部和 epilogue，不用分离读取协程伪装取消。
- 正常完整读完清除接收 deadline；失败保留即时读截止，HTTP/1 关闭连接，防止 handler 返回后继续无限 drain。HTTP/2 单流读取亦有真实 socket 回归。
- 槽和主体计数随原 Upload 生命周期释放；spool 删除/关闭失败仍沿用保守字节保留，不因超时凭空退额。

两层预算协同：公开请求在接收前记录其当前有效预约的内存接收票据。file-first 客户端直到正文结束才提供 UUID，所以先按已认证 owner/request 保护当前有效预约，完成解析后只能使用该快照内的会话。清理在会话 gate 内跳过仍有效的接收票据。它不改持久租约，不允许过期后再开始接收，进程最多 64 张票据，票据最长 2 小时，所有退出路径释放。

首片和后续片只要在原租约内开始接收，持续满足正文预算，就可跨过原到期时间完成（仍受创建后 24 小时上限）。Bind/Progress 在 provider 内再次核对接收开始时间与原到期时间；只有新片落盘才续租，重复片不续租。超时、断流或验证失败释放票据，下一次清理即可回收已到期预约。因此默认 45 MiB 分片在 128 KiB/s 等合法持续传输下，不会仅因超过 5 分钟被误拒绝。没有发送实际数据的请求仍最多占一个 60 秒进展窗口，不能只靠建立连接长期刷新持久预约。

64 KiB/60 秒是有意的最低接收进展预算，极慢连接可能需要重试。小文件只要在窗口内完整结束，不必达到 64 KiB。反向代理自身请求缓冲、传输限速和连接数策略仍需部署者配置，本补丁不替代边缘 DoS 防护。

## 验证范围

新增/更新定向测试覆盖：
- SQLite 与 miniredis 的真实 HTTP receiver→Store 链路：首片/后续片接收期间跨过租约，清理不得误回收；成功新片续租，超时释放后清理。使用注入租约时钟加速，不声称运行了数分钟的 45 MiB 速率压测或整个认证路由。
- SQLite 与 miniredis provider 的初始过期、按需清理、并发预约、reserve/cancel 窗口、有效续租、重复片、跨 request 隔离、绝对上限和零字节完成。
- 清理 gate 忙/失败时不得退额；旧未绑定预约有效期与回执回收。
- 真实 HTTP/1 已知长度和 chunked 请求在五类 multipart 位置停滞；滴流不能刷新；正常持续进展可以完成；真实 HTTP/2 deadline。
- 主体与 request 公平上限、全局容量仍有效，失败后槽/spool 回收，以及既有 receiver/上传入口回归。

这些是合成安全回归，不代表生产压测、真实 Redis、S3、大文件矩阵或真实浏览器验收。测试运行记录随补丁交付，PR 和部署状态由后续本地 Codex 流程确认。

## 剩余边界

- 同一公开链接的持有人无法可靠区分。攻击者仍可竞争该链接的短期准入，或实际发送最低限度的数据占用有限额度；需吊销被滥用的链接或在边缘限速。
- 已绑定后失败/取消的长期回执和异常 I/O 保额仍可能耗尽保守预算。这是避免重复发布/错误释放的既有安全取舍，不声称本组解决整个账本 DoS。
- `SetReadDeadline` 的非网络测试 recorder 不支持路径仅兼容测试；生产自定义 ResponseWriter 必须暴露 `Unwrap` 或实现 deadline，不能隐藏底层连接能力。
- 写入进度已落盘但数据库续租失败时返回失败，不把未知结果当续租成功。重复片不会再延长租约，客户端可能需新建预约重传。

按需清理受账本 4096 条、每 request 256 条上限约束；逐会话持锁重读保证并发正确性，但最坏仍为 O(K×N) 账本处理，本轮未进行生产规模压测。

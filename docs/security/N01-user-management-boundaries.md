# N01：用户管理与文件处置授权边界

基线：`8889084293887b6e16d1362ccacbb79a5e960ccb`。
本批仅对应新安全 CSV 第 1、2 项（用户删除跨文件授权；委派管理者重置高权限账户），不进入 N02。

## 权限矩阵

所有操作先通过现有 API 身份与 MANAGE_USERS 校验。修改权限、改变等级、重置密码和删除用户还共同要求：

- 目标存在、不是自己、不是超级管理员。
- 操作者拥有管理用户权限；目标等级不能高于操作者。
- 目标已有权限必须是操作者权限的子集，防止同等级权限更高账户被接管。
- 晋升为 Admin 会赋予全部权限，因此操作者必须已拥有全部权限；不能借晋升获得自己没有的权限。

普通委派管理者仍可管理权限范围内的普通用户，包括强制修改密码和生成临时密码。管理员身份不绕过权限位。

| 删除账户时的处置 | 用户权限 | API 凭证 | 明确确认 |
| --- | --- | --- | --- |
| 删除文件与 File Request | 跨所有者删除权限 | MANAGE_USERS + DELETE | `deleteFiles=true` |
| 转移文件与 File Request 给当前操作者 | Admin 等级 + 跨所有者编辑权限 | MANAGE_USERS + EDIT | `transferToSelf=true` |

即使目标暂时没有文件，也先校验所选处置权限，避免检查和执行间新增对象绕过授权。不能用“管理用户”代替文件处置权限。

主 API key 可以同时包含两项权限。浏览器使用两个现有短期作用域令牌：主 `apikey` 负责用户管理，可选 `fileOperationKey` 负责 DELETE/EDIT；二者必须属于同一用户，且不得是公开 File Request 上传令牌。无额外令牌时检查主 key 的处置权限。

兼容性变化：旧 API 客户端删除用户时需要补足 DELETE/EDIT 位；保留并转移文件时必须传 `transferToSelf=true`。旧的默认隐式转移不再执行。UI 已同步显示去向和权限说明并提供明确参数。

## 一致性与失败行为

- 用户管理操作按固定顺序锁定操作者和目标，并在锁内重读凭证、操作者和目标。等待期间撤权或目标升级不能使用旧快照继续执行。
- 用户锁与文件/API-key 锁分域，防止删除用户期间嵌套文件锁发生哈希碰撞自死锁。
- 所有授权拒绝发生在会话撤销、API key 删除、文件/请求处置、加密资料和用户行删除之前。认证入口原有访问时间记录不属于业务修改。
- 重置密码使用 SQLite 条件 UPDATE / Redis Lua CAS，只更新密码及强制修改标志；匹配旧密码、重置标志、等级与权限。保留姓名/最后在线时间，不复活已删除用户。CAS 失败不撤销会话。
- 已获授权后的存储 I/O 失败仍遵循既有可重试、保留清理锚点行为，可能部分执行，不承诺整体事务回滚。

## 验证范围

新增测试覆盖权限矩阵、降级后重置链、受限管理员晋升、合法委派重置、锁等待后的撤权/升权、删除和转移的用户/API 双权限、异用户/无效二次令牌、文件与 File Request 同步处置、拒绝后的用户/密码/会话/key/所有权不变，以及用户/文件锁索引碰撞。

SQLite 与 Redis 测试覆盖窄字段保留、四项快照冲突、删除后不复活、空密码与并发 CAS 只能一个成功。

## 不在本批声称解决的范围

此修复不等于登录签发/重置全流程原子化，不实现认证代次，也不提供跨进程操作者撤权事务。N02 的认证/会话竞态单独处理。用户删除和上传并发的完整生命周期协议也不是本次新增保证。
